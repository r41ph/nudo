Step 01 — Critique

—nudo.

Editor interface, main @ ead9a7c
Reviewed against the shipped code and six screen captures

The verdict

The visual language is the strongest part of this product and it is not the part that needs work. The warm editorial palette, the Newsreader prose at a real reading measure, the restraint in the chrome — that is a point of view, and it is rare.

Everything wrong sits in the layer above it. The chrome spends its loudest position telling you about saving rather than writing. The outline hides its own controls behind hover. Most of the sidebar's text fails contrast against the sidebar's own token. And there is no mobile story at all — not a broken one, an absent one.

What the screen is saying

Eight things a first-time writer reads before they read their own sentence.

Dimension by dimension

Visual hierarchy & information architecture
Works
  • The two-zone skeleton — outline rail, single page — is the right shape for long-form. Nothing competes with the prose.
  • Prose at 1.25rem on 1.72 leading in Newsreader is a considered reading measure, not a default.
  • Project name in serif semibold anchors the rail correctly: the book is the top of the hierarchy.
  • The active-row treatment (accent bar, tinted fill, weight shift) is unambiguous without being loud.
Doesn't
  • Chrome outranks content. The status cluster is the visual climax of a writing app.
  • Chapter (13.5px) versus document (12.5px) is one pixel doing the work of a hierarchy level. Indentation and weight carry it alone.
  • Word counts form a third structural column carrying the least useful information on the screen.
  • At 1920px the page holds 800px of measure with ~700px of dead ground to its right, and its bottom edge floats mid-viewport. Tuned for no particular screen.
Accessibility
Most severe
Works
  • Body prose is #3d372e on #f7f3ec — about 9:1. The thing people actually read is comfortably legible.
  • The breadcrumb carries aria-label, aria-current and a real focus ring. Someone was paying attention.
  • Row toggles have state-dependent labels (Collapse / Expand, Fold / Unfold) rather than a static one.
Doesn't
  • Most of the rail's text is below AA. --faint ≈ 1.7:1 (every count, chevron, gear, status dot); --muted-foreground ≈ 2.6:1 (every inactive title, plus Log out / Trash / Help).
  • Every interactive target in the rail is undersized. Rows 32px, separators 28px, row actions and status dots 20px — under the 24px WCAG 2.2 minimum, far under 44px for touch.
  • Add, rename and delete are opacity-0 until row hover: unreachable by keyboard or touch, yet still in the tab order.
  • Delete is a 20px hover-revealed icon with no confirmation that cascades the entire subtree. One misclick loses a chapter.
  • The settings gear is a bare <Icon> — not focusable, unlabelled, and not wired to anything.
  • Outline rows have no :focus-visible style at all, so keyboard position in the tree is invisible.
  • index.css forces color: #4a5d5e !important on the editor while the token layer sets --prose: #3d372e. The !important wins, with a colour that exists in no token file.
Interaction patterns & flow friction
Works
  • Deleting the open document navigates somewhere sensible instead of stranding you — pickAdjacentDocument is real care.
  • Status as an opt-in moon-phase dot is a lovely, quiet idea and exactly the right weight for planning metadata.
  • Autosave at 2.5s with a visible state, and mutation failures surfaced as toasts rather than swallowed.
  • Drag-to-reorder with a dedicated grip, rather than the whole row being draggable.
Doesn't
  • Document / Folder / Separator is a file system's vocabulary, not a novelist's. “Separator” is a formatting word for a thing the code itself titles “Part”.
  • Same menu, two consequences: creating a folder navigates you into a document you didn't ask to open; creating a separator doesn't navigate at all.
  • Two entry points (footer “New”, row “+”) look identical and produce root versus child, with nothing indicating which.
  • The toolbar only exists on selection. FixedToolbar is commented out, so there is no way to set a heading on an empty line — and the whole customisable-toolbar feature is undiscoverable until you select text and notice a gear.
  • The persistent save element is the least useful one (a stale timestamp); the reassuring one (“Saved”) auto-hides after 4s.
  • Rename swaps the row for a bare input — count, status and position markers all vanish mid-edit, and blur commits silently.
  • Focus mode hides everything including the outline, exits only via a 28px ghost button, and has no Escape handler.
  • No search, and “+0 today” implies a daily goal the product never lets you set.
Consistency & design system coherence
Works
  • The token layer is genuinely above average: semantic names, complete light/dark pairs, and domain tokens (--prose, --faint, --comment, --status-*) where shadcn has no equivalent.
  • Every token is commented with the design-handoff name it came from. The provenance is traceable.
  • Feature-sliced architecture with a shared UI package keeps the component vocabulary in one place.
Doesn't
  • The chrome routes around the tokens. SaveBar uses four raw Tailwind colours (orange-500, yellow-600, red-600, green-800) in forty lines — none tokenised, none with a dark variant, while the one status colour that is tokenised goes unused.
  • Five arbitrary type sizes in the chrome alone (13, 13.5, 12.5, 11, 10.5px). There is no scale, only measurements.
  • Three radii in play — rounded-[7px] rows, rounded-sm page — and the declared --radius: 0.625rem is used by neither.
  • Two vocabularies for the same states: text-gray-500 / text-red-500 on the document page, text-destructive on the home page.
  • Two identical logo files swapped by dark:hidden, duplicated across two components, where one currentColor mark would do.
  • Sidebar collapsible="none" discards the entire reason the shadcn sidebar exists.
Mobile responsiveness
Not attempted
Works
  • The pieces are all already vendored — use-mobile, Sheet, and a shadcn sidebar with a built-in off-canvas mode. Nothing needs building, only wiring.
  • Focus mode is, effectively, the mobile editor already: chrome off, prose only.
Doesn't
  • WorkspaceLayout is a bare flex with a fixed rail and no breakpoint anywhere, and collapsible="none" means the rail can never get out of the way. Below ~700px the editor is simply squeezed off-screen.
  • Editor padding is px-16 below the sm breakpoint, plus the layout's px-8: on a 375px screen that leaves roughly 250px of measure — about four words a line.
  • use-mobile.ts and Sheet are both imported by nothing. The intent was there and never landed.
  • The floating selection toolbar is the only formatting surface, and text selection is the single hardest gesture on a touch device.

What I would fix, in order

Ordered by harm done per hour of work, not by how visible the change is.

01
Confirm destructive deletes

A hover-only 20px icon that cascades a subtree with no undo is the one bug here that loses a person's work.

02
Darken --faint and --muted-foreground

Two token values fix most of the sidebar at once. The palette's character survives it.

03
Make row actions reachable

One 28px row menu instead of three 20px hover icons: keyboard-reachable, touch-sized, and quieter.

04
Demote the status cluster

One state, one token colour, minute precision. Give the reclaimed space to the document's own title.

05
Let the page end where the text ends

Drop the fixed height and the shadow. A column of prose on the ground needs no container.

06
Wire the rail's collapse and the Sheet

The mobile layout is two props and one breakpoint away from existing. Both components are already in the repo.
